  • Axe Y (Médio-latéral)Mesure la stabilité latérale et la pronation.

  • Rollback AutomatiqueProbation 15s : retour instantané à l'ancienne version si l'IMU ne répond pas.
[Notes Orateur - 02:30 à 05:00] :
Sur la chaussure, l'ESP32-S3 communique avec l'IMU en I2C à 400 kHz. L'alignement suit le standard biomécanique ISB : l'axe Z vertical mesure la gravité (+1g statique), X la propulsion et Y la stabilité. Le vibreur haptique est piloté en PWM à 10 kHz pour des alertes discrètes ou franches. Comme la semelle est hermétique, les mises à jour se font par BLE OTA. Le binaire est vérifié par SHA-256, et un rollback automatique restaure l'ancien firmware si le capteur ne répond pas dans les 15 secondes.

L'IA embarquée traite le signal à 19 Hz sur une fenêtre glissante de 2 secondes. Pour éviter les fausses alertes, nous combinons l'IA avec une garde biomécanique : détection de choc > 16.2 m/s² suivie d'une vérification de l'immobilité anormale au sol.
Cycle d'Entraînement
Boucle MLOps : Du Terrain au Code C Embarqué

1. MODE STUDIO HAUTE FRÉQUENCE

Acquisition brute (54 / 100 Hz) déclenchée depuis l'application. Streaming en burst BLE avec contrôle CRC32 vers DynamoDB pour constituer les jeux de données.

2. STRATIFIED 5-FOLD CROSS VALIDATION

Cache local incrémental pour minimiser les coûts AWS. 5 plis stratifiés garantissant la même proportion de chutes rares. Optimisation sur le Macro F1-score.

3. TRANSPILATION C PURE SANS RUNTIME (m2cgen)

Conversion automatique du modèle scikit-learn en C standard (activity_model_generated.h). Aucun framework lourd (zéro TFLite). Exécution en ~12 µs.

4. QUALITY GATE & CONTRÔLE DU FIRMWARE

Quality Gate bloquant : Macro F1-score ≥ 85% obligatoire. Compilation automatique PlatformIO (pio run) validant les quotas Flash/RAM avant tout déploiement.

[Notes Orateur - 08:00 à 10:30] :
L'entraînement est automatisé par notre script update_edge_model.py : le mode Studio enregistre des sessions réelles à 54 ou 100 Hz ; l'évaluation utilise une validation croisée stratifiée en 5 plis (Stratified 5-Fold) pour répartir équitablement les chutes rares et optimiser le Macro F1-score ; le modèle champion est transpilé en C pur via m2cgen en 12 microsecondes sans aucun framework externe ; et un Quality Gate bloque la mise à jour si le F1-score est inférieur à 85%.
Gestion des Données
Réseau & Podométrie Différentielle Nette
PODOMÉTRIE DIFFÉRENTIELLE (SQLite)
  • Compteur Matériel MonotoneL'ESP32 incrémente ses pas continuellement sans date ni heure.
  • Calcul du Delta NetLe mobile compare chaque snapshot : delta = current - previous.
  • Résilience aux RedémarragesSi current < previous (reboot chaussure), le delta s'adapte sans perte.
  • Bascule Propre à MinuitLe compteur matériel continue mais le delta est isolé pour le nouveau jour.
  • Ventilation Horaire RéelleEnvoi par tranche horaire réelle (hourly_steps) sans heuristique artificielle.
PASSERELLE TEMPS RÉEL (AWS IoT Core)
  • WebSockets MQTT PersistantSession maintenue ouverte en tâche de fond pour latence minimale.
  • Authentification SigV4Signature cryptographique avec clé temporaire STS (15 min).
  • Alerte de Chute (QoS 1)Publication immédiate avec accusé de réception vers AWS IoT Core.
  • Supervision de LiaisonNotification de l'état de connexion Bluetooth et réseau.
  • Commandes HaptiquesDéclenchement distant d'une vibration via topic commands/haptic.
[Notes Orateur - 10:30 à 12:30] :
Pour la podométrie, l'ESP32 possède un compteur monotone physique qui ne connaît pas les jours. Notre application mobile implémente une odométrie différentielle SQLite : elle calcule le delta net de pas, gère les redémarrages de chaussure et ventile les pas heure par heure de manière 100% réelle. Pour les alertes, le mobile maintient une connexion WebSockets MQTT signée en SigV4 vers AWS IoT Core, ce qui permet d'envoyer l'alerte de chute en quelques dizaines de millisecondes aux proches.
